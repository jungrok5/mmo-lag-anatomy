# 게임 렉 백서

온라인 게임에서 렉이 생기는 원인을 **내 게임 화면부터 서버의 데이터베이스까지 13개 층**으로 나눠 설명하고,
슬라이더와 스위치로 직접 망가뜨려 보며 이해하는 시청각 백서입니다. MMO 사례를 중심으로 썼지만, 대부분은 장르와 상관없이 온라인 게임 전반에 해당합니다.
서버 프로그래머가 아닌 기획·아트·QA·PM이 읽는 것을 기준으로 썼습니다.

**사이트: https://jungrok5.github.io/mmo-lag-anatomy/**

`index.html` 하나를 브라우저로 열면 됩니다. 글꼴까지 파일 안에 들어 있어 외부 서버나 인터넷 연결 없이 열립니다(출처 링크를 누를 때만 외부로 나갑니다).
웹 서버, GitHub Pages, 공유 폴더 어디에 올려도 되고, 외부 인터넷이 막힌 환경에서도 같은 모양으로 보입니다.

원인 항목은 228개(레이어 13개 168개, 동기화 설계 16개, 일부에게만 생기는 문제 24개, TCP 재전송 20개)이고 용어는 135개입니다. 각 원인 항목은 **왜 → 그러면 → 화면에서는**의 세 단계와
관련 증상, 네 가지 요인, 누가·언제 겪는지, 수치 감각, 해결 담당(게임개발팀·인프라팀·외부)과 팀별 할 일, **그래프 모양**(13가지)과 **확인 방법**(확인할 곳, 이러면 맞음·아님, 확인 수단)을 담고 있습니다.
주 담당 기준으로 게임개발팀 136개(클라이언트 40, 서버 96), 인프라팀 64개(네트워크 25, 서버 장비·OS 33, DB 장비 6), 외부(유저 환경·통신사·클라우드) 28개이고, 95개는 두 팀 모두 할 일이 있습니다.
가장 쉬운 확인 수단으로 나누면 인프라 도구(게임 코드 없이) 125개, 게임 로그·지표 61개, 유저 쪽 42개입니다. 특정 회사의 지표·도구 없이 공개 도구와 공식 지표 이름만 씁니다.

## 원인 ID로 가리키기

원인 카드마다 **ID**(예: `mem-gc`)와 **링크 복사** 버튼이 있습니다. 장애 기록이나 티켓, 문서에 이 링크를 붙이면 그 원인 카드가 펼쳐진 채로 열립니다(주소 끝 `#c-mem-gc`).
기록과 백서를 대조하는 기준 값이라서, ID는 한번 정하면 바꾸거나 지우지 않습니다.

## Claude로 묻기

- **Claude Code로 이 저장소를 열 때**: [`CLAUDE.md`](CLAUDE.md)에 데이터 위치, 필드 뜻, 증상에서 원인과 담당을 좁히는 방법, 장애 기록 대조 절차가 있어 그대로 따라 답합니다.
- **Claude 프로젝트에 자료로 올릴 때**: `npm run export`로 만든 `build/lag-anatomy.md`(원인·증상·담당·용어·출처 전체)를 올립니다. 스크립트로 대조할 때는 같은 내용의 `build/lag-anatomy.json`을 씁니다.

## 검색엔진·AI가 읽는 파일

원인 카드·증상 사전·용어는 자바스크립트가 그리는데, AI 수집기(ChatGPT·Claude 등) 상당수는 자바스크립트를 실행하지 않습니다. 그래서 배포할 때 `tools/site.cjs`가 같은 내용을 정적 파일로도 만듭니다.

| 주소 | 내용 |
|---|---|
| `c/<원인 ID>.html` | 원인마다 한 페이지(228개). 제목·설명·출처·구조화 데이터(JSON-LD)를 따로 가져 질문과 딱 맞는 페이지로 인용되기 쉬움 |
| `s/<증상 ID>.html` | 증상마다 그 증상을 만드는 원인 목록 |
| `text.html` | 전체를 한 페이지로 읽는 텍스트 판 |
| `llms.txt`, `llms-full.txt` | AI용 안내와 전체 내용 마크다운([llmstxt.org](https://llmstxt.org) 형식) |
| `sitemap.xml` | 검색엔진용 주소 목록 |
| `index.html` | 원본에 원인·증상·용어의 정적 사본을 더한 것. 스크립트가 돌면 원래 화면으로 바뀜 |

배포 워크플로가 끝나면 IndexNow로 Bing·Naver 등에 바뀐 주소를 알립니다. 링크 미리보기 이미지는 `node tools/og.cjs`로 다시 만듭니다. 사이트 주소는 `package.json`의 `homepage` 한 곳에만 적습니다.

## 검수

영역별 시니어 개발자 관점의 AI 검토자 7명이 전체를 검수했고(지적 161건), 이어서 4명이 TCP 재전송 장을 다시 검수했습니다(지적 67건). 3차로 8명이 문서 전체를 영역별로 다시 검수했고(지적 212건), 이어서 장 사이의 수치를 맞추는 편집과 비전문가 눈높이의 쉬운 말 편집을 거쳤습니다. 숫자·기본값·버전은 커널 소스, RFC, 클라우드·엔진 공식 문서로 확인했고, 27개 실험은 모든 프리셋을 헤드리스 브라우저로 돌려 해설 숫자와 모델 값이 맞는지 확인했습니다. 게임개발팀·인프라팀 담당 구분도 영역별 검토자 5명과 장애 대응 책임자 관점의 교차 검토자가 검수했습니다. 마지막으로 원인 216개 전부와 21개 장에 공신력 있는 출처(표준 문서, 커널·OS·클라우드·엔진·DB 공식 문서, 논문, 원개발사 기술 글)를 달면서 자료와 다른 문장을 고쳤습니다(서로 다른 자료 436건, 발행처 65곳). 출처는 사이트의 원인 카드, 장 끝, “참고 문헌” 장에 있습니다. 공개 직전에는 영역별 검토자 6명이 사실·출처·장 사이 수치·담당·접근성·도구를 한 번 더 검수했습니다. 공개 뒤에는 사내 데이터 없이도 원인을 판정할 수 있게 원인 12개, 모든 원인의 그래프 모양·확인 방법, 공개된 장애 사후 분석 12건과 상황별 절차 2개를 더하고, 영역별 검토자 5명이 원문과 공식 문서로 다시 대조했습니다(출처 주소 630개, 발행처 83곳). 반영 결과는 [`REVIEW.md`](REVIEW.md)에 있습니다.

```
docs/TERMS.md         표준 용어표(비유어 대신 쓸 통용 용어)
docs/SOURCES_GUIDE.md 출처 작성 규칙(공신력 있는 자료만)
docs/CHECKS_GUIDE.md  그래프 모양(sig)·확인 방법(chk) 작성 규칙
docs/OBSERVABILITY_PLAN.md  관측으로 원인·담당을 판정하는 계획(사이트의 “관측으로 판정하기” 장의 바탕)
REVIEW.md             영역별 검수 기록
```

## 고치고 다시 만들기

처음 한 번: `npm install` 후 `npx playwright install chromium` (Node 18 이상, Python 3.9 이상).

```bash
npm test                                      # 빌드 + 데이터 검사 + 1280px·390px 다크 점검
python3 build.py                              # index.html 생성
node tools/validate.cjs                       # 원인 데이터 검사
npm run links                                 # 출처 주소 점검
npm run export                                # build/lag-anatomy.md·.json 내보내기
npm run site                                  # 배포본을 build/site/ 에 만들기(원인·증상별 페이지 등)
python3 build.py --only lab                   # 시뮬레이션 하나만 build/sandbox-lab.html 로
node tools/check.cjs index.html build/p.png 1280          # 오류 확인 + 스크린샷
node tools/check.cjs index.html build/m.png 390 --dark    # 폰 폭, 다크 모드
```

원인 항목을 추가하려면 `src/js/causes-*.js` 의 해당 레이어 목록에 객체 하나를 넣으면
그 장의 원인 카드, 증상 사전의 역색인, 진단 도우미 점수에 자동으로 반영됩니다.
해결 담당은 `own`(첫 항목이 주 담당: `cli` 클라이언트 개발, `srv` 서버 개발, `net` 네트워크 인프라, `sys` 서버 인프라, `dba` DB 인프라, `ext` 외부)과
`act`(`game`·`infra`·`ext` 팀별 할 일)로 적고, 담당 구분 장의 표와 탐색기, 레이어 머리말, 진단 도우미에 자동으로 반영됩니다.

## 기여하기

오류 제보, 출처 제안, 원인 추가 모두 이슈나 풀 리퀘스트로 받습니다.

1. 원인은 `src/js/causes-*.js`, 본문은 `src/body.html`, 용어는 `src/js/glossary.js`에서 고칩니다. `index.html`은 직접 고치지 않습니다.
2. 필드와 문장 규칙은 [`CLAUDE.md`](CLAUDE.md), 담당은 [`docs/OWNERS_GUIDE.md`](docs/OWNERS_GUIDE.md), 그래프 모양·확인 방법은 [`docs/CHECKS_GUIDE.md`](docs/CHECKS_GUIDE.md), 용어는 [`docs/TERMS.md`](docs/TERMS.md), 출처는 [`docs/SOURCES_GUIDE.md`](docs/SOURCES_GUIDE.md)를 따릅니다. 수치·기본값을 바꿀 때는 공신력 있는 출처(`ref`)를 함께 답니다.
3. 원인 ID(`id`)는 바꾸거나 지우지 않습니다. 다른 곳의 기록이 이 ID로 원인을 가리킵니다.
4. `npm test`가 통과하는지 확인하고, 다시 만든 `index.html`을 함께 커밋합니다(배포하는 파일입니다).
