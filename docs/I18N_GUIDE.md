# 번역 규칙 (I18N)

한국어가 원문이다. 번역판은 원문과 같은 사실을 그 언어의 시니어 게임 개발자·인프라 엔지니어가 쓴 것처럼 옮긴다. 기계 번역투, 직역, 한국어 어순을 따라간 문장은 쓰지 않는다. 사실을 더하거나 빼지 않는다.

## 언어와 주소

`src/i18n/langs.json`. 한국어는 사이트 맨 위(`/`), 번역판은 `/<dir>/`(예: `/en/`, `/zh-tw/`)에 있다. 원인 ID, 장·절 ID, 사례·절차 ID는 모든 언어에서 같다. 그래서 `#c-mem-gc` 같은 주소 끝은 언어를 바꿔도 그대로 쓸 수 있다.

| code | 언어 | 대상 |
|---|---|---|
| en | English | 미국 영어 |
| ja | 日本語 | 일본 |
| zh-CN | 简体中文 | 중국 대륙의 용어(服务器, 数据包, 内存, 线程) |
| zh-TW | 繁體中文 | 대만의 용어(伺服器, 封包, 記憶體, 執行緒). 간체를 글자만 바꾼 것이 아니다 |
| de | Deutsch | 독일 |
| th | ไทย | 태국 |
| vi | Tiếng Việt | 베트남 |
| ru | Русский | 러시아 |

## 파일

- `src/i18n/<code>/<묶음>.json`: 번역 단위 목록. 한 줄에 항목 하나 `{"ctx": 자리, "ko": 원문, "t": 번역}`.
- 묶음: `causes-<층>`(원인), `data`(증상·층·팀 이름 등), `glossary`, `cases`(사례·절차), `refs`(장별 출처의 설명), `body-<장>`(본문), `ui-app`·`ui-kit`(화면 글자), `sim-<실험>`(실험의 글자), `site`(원인별 페이지·llms.txt·제목), `meta`(검색 설명).
- `docs/i18n/<code>.md`: 그 언어의 용어표와 문체 규칙. 번역하는 사람은 반드시 먼저 읽고 따른다.
- 원문 `ko`가 사전의 열쇠다. 원문이 바뀌면 그 항목은 빈 칸이 되고 옛 번역은 `stale`에 남는다(`sync`).

## 명령

```bash
node tools/i18n.cjs sync               # 원문에 맞춰 모든 언어의 번역 파일을 만들거나 고친다
node tools/i18n.cjs status --groups    # 언어·묶음별 번역률
node tools/i18n.cjs show en causes-memory --empty --from 0 --count 40   # 번역할 항목을 번호와 함께
node tools/i18n.cjs fill en causes-memory batch.json    # {"번호": "번역"} 을 t에 채운다(형식 검사 결과를 함께 출력)
node tools/i18n.cjs check en --warn    # 자리표시·태그·링크·숫자 검사
python3 build.py --lang en             # build/i18n/en/index.html
node tools/site.cjs                    # 모든 언어의 배포본
```

## 반드시 지킬 형식

- **자리표시** `{0}`, `{1}` …: 원문에 있는 것을 모두, 그대로 둔다. 순서는 그 언어 어순에 맞게 바꿔도 된다. 자리에는 숫자·이름·HTML 조각이 들어간다(`ctx`의 파일·줄에서 확인).
- **HTML 태그**: 원문의 태그를 모두 같은 개수로 둔다. `href`·`id`·`class`·`data-*` 값은 그대로, `aria-label`·`title`·`alt`는 번역한다. 속성값 번역(`ctx`가 `@aria-label` 등)에는 `"` `<` `>`를 쓰지 않는다.
- **그대로 두는 것**: 원인 ID, 명령·옵션·카운터·지표 이름(`ss -ti`, `TcpExtTCPLostRetransmit`, `pg_stat_statements`), 제품·도구 이름, RFC 번호, 주소, `%SITE%`, 코드 조각(`<code>` 안).
- **숫자**: 값은 바꾸지 않는다. 쓰는 법(천 단위·소수점 기호, 단위 띄어쓰기)은 그 언어 관례를 따른다. `ms`, `µs`, `Gbps` 같은 단위 기호는 그대로.
- **복수형**: 자리에 수가 들어가는 짧은 글자(“원인 {0}가지”)는 러시아어처럼 수에 따라 꼴이 바뀌는 언어에서 “Причин: {0}”처럼 수와 일치시키지 않아도 되는 꼴로 쓴다.

## 문체

- 원문의 규칙을 그 언어에 맞게 지킨다: 비전문가(기획·아트·QA·PM)가 읽는다고 생각하고 쉽게, 비유 대신 그 나라 업계의 통용 용어로, 문장 가운데에 대시(—)로 설명을 끼워 넣지 않고, “A가 아니라 B” 꼴(“not A but B”, “AではなくB”, “不是A而是B”)을 쓰지 않는다.
- **증상 이름 11개**는 `docs/i18n/<code>.md`에 정한 이름을 어디서나 똑같이 쓴다. 그 나라 플레이어·개발자가 실제로 쓰는 말로 정한다.
- 원문의 본문은 존댓말(합니다체), 확인 방법(`chk`)은 개조식이다. 번역도 본문은 그 언어의 정중한 설명체, 확인 방법은 짧은 명사형·체언 끝맺음으로 쓴다.
- 한국 통신사·기관 이름처럼 원문에 있는 고유한 사실은 그대로 옮긴다(다른 나라 예로 바꾸지 않는다).

## 검색·AI 인용

- `meta`(검색 설명), `site`의 제목(`… | 게임 렉 백서`), 사이트 이름은 그 언어로 사람들이 실제로 검색하는 말(예: “lag 원인”에 해당하는 현지 표현)을 자연스럽게 넣는다. 낱말을 늘어놓지 않는다.
- 사이트 이름: 영어 “Game Lag White Paper”. 다른 언어는 `docs/i18n/<code>.md`에 정한 이름을 쓴다.
- 빌드가 언어판마다 `hreflang`, `og:locale`, 구조화 데이터의 `inLanguage`·`translationOfWork`, 언어별 `llms.txt`·`llms-full.txt`·원인별 페이지·sitemap을 만든다.

## 검수

언어마다 그 언어가 모국어인 시니어 게임 서버·클라이언트·인프라 개발자 관점의 검토자가 원문과 대조해 본다: 사실이 같은지, 용어가 그 나라 업계 통용어인지, 번역투가 없는지, 증상 이름·용어가 일관된지, 숫자·명령이 그대로인지. `node tools/i18n.cjs check <code> --strict`가 오류 0이어야 배포한다.
