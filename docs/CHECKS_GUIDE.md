# 그래프 모양(sig)·확인 방법(chk) 작성 규칙

원인 카드마다 “이 원인이면 모니터링 그래프가 어떻게 보이는지(sig)”와 “무엇을 보면 이 원인인지 확인되는지(chk)”를 넣는다. 사이트의 원인 카드, 원인별 페이지, “관측으로 판정하기” 장에 자동으로 나온다.

이 백서는 특정 조직의 데이터 없이 완결되어야 한다. 특정 회사의 지표 이름·대시보드·내부 도구는 쓰지 않고, 누구나 쓰는 공개 도구와 공식 지표 이름만 쓴다.

## 형식

```js
sig: { k: 'periodic', g: '서버 틱 시간, GC 로그의 멈춤 시간' },
chk: {
  look: 'JVM 시작 옵션 -Xlog:gc*로 남긴 GC 로그의 멈춤 시간과 서버 틱 시간 그래프',
  yes: '틱이 튄 시각과 GC 멈춤 시각이 겹치고, 멈춤 길이가 튄 길이와 비슷함',
  no: 'GC 로그에 긴 멈춤이 없는데도 틱이 튀면 락·동기 호출 같은 다른 원인',
  by: 'ops',
},
```

필드는 `ref` 앞에 둔다(원인 항목의 마지막은 `ref`). 모든 원인에 두 필드가 있어야 하고, 빠지면 `node tools/validate.cjs`가 오류로 잡는다.

### sig: 그래프 모양

- `k`: 아래 13가지 중 하나(`src/js/data.js`의 `sigs`). 이 원인이 생겼을 때 **가장 먼저 눈에 띄는 그래프**의 모양으로 고른다.
- `g`: 그 모양이 보이는 그래프 이름. 짧게, 1~3개. 예: “RTT(핑)”, “서버 틱 시간”, “재전송률”, “코어별 CPU 사용률”, “접속 수·끊김 수”, “DB 쿼리 지연”, “디스크 대기열 길이”, “프레임 시간”.

| k | 이름 | 모양 | 예 |
|---|---|---|---|
| `periodic` | 일정 주기로 튐 | 같은 간격으로 솟음 | GC, 크론·백업, 타이머 몰림, 체크포인트 |
| `random` | 가끔 무작위로 튐 | 불규칙하게 솟았다 돌아옴 | 와이파이 간섭, 손실 뭉치, 프레임 스파이크 |
| `step` | 어느 순간부터 계단처럼 올라감 | 특정 시각 뒤 한 단계 올라가 머묾 | 패치, 설정 변경, 경로 변경, 장애 전환 |
| `ramp` | 서서히 오름 | 몇 시간·며칠에 걸쳐 증가 | 메모리 누수, 개체 누적, 단편화 |
| `sawtooth` | 서서히 오르다 뚝 떨어짐 | 오르다 재시작·정리 때 급락, 반복 | 재시작으로 버티는 누수, 테이블이 찼다 비워짐 |
| `peak` | 특정 시간대에만 높음 | 하루 중 같은 시간대 언덕 | 피크 시간 피어링 혼잡, 저녁 부하 |
| `load` | 인원·부하를 따라 오름 | 인원 증가보다 가파르게 오름 | 시야 계산 N², 브로드캐스트, 핫스팟, 락 경합 |
| `ceiling` | 한도에 닿아 평평해짐 | 처리량·연결 수가 한 값에서 멈추고 대기·오류 증가 | PPS 한도, 커넥션 풀 고갈, fd 한도, IOPS 한도 |
| `high` | 처음부터 늘 높음 | 튀지 않고 계속 높음 | 물리적 거리, 우회 경로, 요청-응답 설계 |
| `outlier` | 일부만 높음 | 대부분 정상, 특정 유저·지역·기기만 높음 | 한 유저의 와이파이, 특정 통신사, 특정 기기 |
| `gap` | 끊겼다가 몰아서 | 받은 양이 0으로 비었다가 몰려옴 | TCP HOL·RTO, 멈춘 뒤 따라잡기 |
| `drop` | 연결이 한꺼번에 끊김 | 접속 수 급락 또는 끊김 수 급등 | 유휴 타임아웃, 크래시, 장애 전환, 인증서 만료 |
| `surge` | 접속·점검 직후 폭증 | 시작 직후 솟았다 가라앉음 | 로그인 폭주, 재시도 폭풍, 콜드 캐시 |

### chk: 확인 방법

- `look`: 확인할 곳. 어떤 지표·로그·명령을 어디서 보는지. 한두 문장.
- `yes`: 이렇게 보이면 이 원인. 판정 기준을 구체적으로(“튄 시각이 X와 겹침”, “카운터 Y가 증가”).
- `no`: 이렇게 보이면 이 원인이 아님(배제 기준). 헷갈리기 쉬운 다른 원인으로 넘어가는 단서면 더 좋다. 쓸 게 없으면 생략.
- `by`: 가장 쉬운 확인 수단.
  - `ops`: 인프라 도구로 확인. OS·네트워크·클라우드·DB 도구, 런타임 시작 옵션(GC 로그 등). 게임 코드를 고치지 않아도 된다.
  - `code`: 게임 서버·클라이언트가 남기는 로그·지표(틱 시간, 끊김 사유, 게임 안 RTT 등)가 있어야 확인된다.
  - `user`: 유저 PC·회선·기기에서 확인해야 한다(넷그래프, 유선으로 바꿔 보기 등).

## 쓸 수 있는 도구 예

- **리눅스**: `ss -ti`, `nstat -az`, `mpstat -P ALL`, `pidstat -t`, `vmstat`, `sar`, `iostat -x`, `ethtool -S`, `dmesg`, `/proc/pressure/*`(PSI), `conntrack -S`, `tc -s qdisc`, `perf`, bcc(`tcpretrans`, `runqlat`, `offcputime`)
- **윈도우**: 성능 모니터 카운터, `netsh int tcp show global`, `pktmon`, PresentMon(프레임 시간)
- **네트워크**: `mtr`, `ping`, `traceroute`, Wireshark, 스위치·방화벽의 인터페이스 카운터
- **클라우드**: 공식 지표 이름 그대로(예: CloudWatch의 EC2 `CPUCreditBalance`, EBS `BurstBalance`·`VolumeQueueLength`, NAT 게이트웨이 `ErrorPortAllocation`, ENA `ethtool -S`의 allowance 카운터)
- **DB**: MySQL `performance_schema`·slow query log·`SHOW ENGINE INNODB STATUS`, PostgreSQL `pg_stat_activity`·`pg_locks`·`pg_stat_statements`, Redis `SLOWLOG`·`INFO`·`LATENCY`
- **런타임**: JVM `-Xlog:gc*`, .NET `dotnet-counters`, Go `GODEBUG=gctrace=1`
- **게임 쪽(있다면)**: 틱 시간, 존·채널별 인원, 끊김 사유 코드, 게임 안 RTT·넷그래프, 클라이언트 프레임 시간

## 정확성

- 명령·카운터·지표 이름은 실제로 존재하는 것만 쓴다. 공식 문서(man 페이지, 클라우드·DB·런타임 문서)로 확인한다.
- 원인의 기존 출처로 뒷받침되지 않는 새 사실(카운터 이름, 기본값 등)을 넣으면 그 근거를 `ref`에 더한다(`docs/SOURCES_GUIDE.md`).
- “이렇게 보이면 맞음”은 단정할 수 있는 만큼만 쓴다. 다른 원인도 같은 모양을 낼 수 있으면 `no`에 구분 단서를 적는다.

## 문장 규칙

`CLAUDE.md`의 문장 규칙을 따른다. 비전문가도 읽을 수 있게 쉬운 말로, 통용 용어로 쓴다. 대시(—)로 설명을 끼워 넣지 않고, “A가 아니라 B” 꼴을 쓰지 않는다. 증상은 `data.js`의 증상 이름 그대로 쓴다.

- `look`·`yes`·`no`는 개조식으로 끝낸다(“~봄”, “~함”, “~늘어남”). 문장이 둘이면 가운데만 마침표를 찍고 끝에는 찍지 않는다.
- 화면에 HTML로 그대로 들어가므로 꺾쇠(`<`, `>`)를 쓰지 않는다. “PID”처럼 말로 쓴다.
