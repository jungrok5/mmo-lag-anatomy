# 관측으로 판정하기: 인프라팀이 렉의 원인과 담당을 가리는 방법

이 문서는 계획입니다. 절차와 신호표는 바로 쓸 수 있습니다. 6장의 백서 기능 가운데 1~4번과 8번은 사이트의 “관측으로 판정하기”·“사례와 절차” 장과 원인 카드에 들어갔고 5~7번은 각 조직이 자기 환경에 맞춰 만들 몫이라 백서에는 넣지 않습니다.

## 배경과 목표

게임 서비스의 인프라팀은 흔히 서비스에 필요한 모든 것을 맡고 장애는 주로 렉과 “무엇이 안 보인다”는 제보입니다. 네트워크·장비·DB의 메트릭은 Zabbix·Grafana 같은 도구로 깊게 쌓아도, 클라이언트·서버 코드를 볼 수 없고 게임 개발 배경이 없으면 다음이 어렵습니다.

- 제보된 현상이 왜 생기는지 이해하기
- 인프라팀이 추적할 일인지, 인프라팀이 해결할 수 있는 일인지 판단하기
- “잘되던 것이 어느 패치 이후 문제”, “국내는 괜찮은데 해외 국가를 추가하니 문제” 같은 경우를 게임 개발 쪽 이해를 바탕으로 풀기

목표는 세 가지입니다.

1. 개발 코드를 몰라도 현상의 원인을 좁힌다.
2. 어느 팀이 추적·해결할 일인지 판정한다.
3. 클라이언트·서버 코드 연동은 최소로, 가능하면 없이 한다.

## 진단: 메트릭을 쌓아도 부족한 것은 연결 고리

1. **차원**: 유저 제보와 메트릭을 잇는 기준(국가·통신사(ASN)·서버·채널·빌드·기기·세션)이 없다.
2. **앱 상태 신호**: 게임 서버·클라 안에서 무슨 일이 있는지 보여 주는 신호가 거의 없다. 상당수는 코드 없이 OS 밖에서 볼 수 있다.
3. **판정 규칙**: “이 그래프가 이렇게 보이면 이 팀”이라는 규칙이 없다.

그래서 백서를 “읽는 백과”에서 “판정 도구”로 한 단계 올린다.

## 1. 판정 순서: 범위 → 시점 → 계층

백서의 진단 도우미가 쓰는 누가·언제·모양을 그대로 운영 절차로 옮긴다.

1. **범위**: 이상이 어느 차원에 몰렸나. 담당이 가장 크게 갈리는 단서다.
2. **시점**: 배포·패치·설정 변경·네트워크 작업·이벤트·크론과 겹치나.
3. **계층**: 네트워크 → 호스트 → 게임 서버 앱 → DB → 클라 중 어디가 비정상인가.

### 판정 신호표

| 확인할 것 | 이렇게 보이면 | 먼저 부를 곳 |
|---|---|---|
| 이상이 몰린 차원 | 특정 국가·ASN·통신사 | 네트워크 / 외부 |
| | 특정 서버·채널·존 | 호스트 지표가 정상이면 서버 개발, 비정상이면 서버 인프라 |
| | 특정 OS·기기·빌드 | 클라이언트 |
| | 전체 동시 | 공용 자원(DB·LB·게이트웨이) 또는 방금 나간 배포 |
| 서버 소켓 Recv-Q | 서버 프로세스가 못 읽어 쌓임 | 서버 개발 (틱 멈춤·GC·락) |
| Send-Q, 연결별 재전송·RTT | 일부 연결만, 특정 ASN에 몰림 | 경로·유저 회선 |
| | 한 호스트의 모든 연결 | 서버 인프라 (NIC·커널) |
| 패치 직후 서버 전체 재전송 증가 | 패킷 크기·버스트 모양이 바뀜 | 서버 개발 + 네트워크 (MTU·몰림) |
| CPU steal·스로틀링·softirq·NIC 드롭 | 증가 | 서버 인프라 |
| 한 스레드만 100%, 런큐 지연, GC 로그 멈춤 | 증가 | 서버 개발 |
| DB 지연 증가, QPS 그대로 | IOPS·잠금·다른 작업 | DB 인프라 |
| DB QPS·쿼리 모양이 패치 후 변함 | N+1, 새 쿼리 | 서버 개발 |
| 해외 합성 측정의 RTT·손실 | 나쁨 | 네트워크 / 외부 |
| 합성 측정은 정상인데 유저만 나쁨 | 유저 환경 또는 클라 | 외부 / 클라이언트 |
| 클라 요약: FPS·프레임 스파이크 나쁨, RTT 정상 | 클라 성능 | 클라이언트 (또는 유저 기기) |
| 클라 요약: 틱 번호 공백, RTT 정상 | 서버가 업데이트를 못 보냄 | 서버 개발 |
| 끊김 사유 분포 | 하트비트 타임아웃↑ / RST↑ / 서버 킥↑ | NAT·경로 / 장비 / 서버 |
| 정확한 주기(정각, N분) | 크론·백업·GC·이벤트 | 그 스케줄의 주인 |

## 2. 코드 없이 바로 할 수 있는 것

- **차원 붙이기**: 접속 로그·LB 로그·flow 로그의 클라 IP에 GeoIP·ASN을 붙인다(MaxMind GeoLite2, IPinfo 등). 개인정보는 /24나 ASN 단위로 줄여 보관한다. “해외만”, “특정 통신사만”이 바로 보인다.
- **서버 연결 품질**
  - TCP: eBPF(`ebpf_exporter`, bcc `tcpretrans`·`tcprtt`·`tcplife`) 또는 `ss -tin` 주기 샘플로 연결별 RTT·재전송을 ASN별로 집계한다.
  - UDP: 흐름별 pps·바이트, `UdpRcvbufErrors`. 프로토콜 명세만 있으면 패킷 헤더의 시퀀스 번호로 손실을 추정할 수 있다(코드 변경 없음).
- **서버 밖에서 서버 속 보기**
  - 소켓 Recv-Q/Send-Q, 스레드별 CPU(`pidstat -t`), 런큐 지연(`runqlat`), off-CPU(`offcputime`)
  - 시작 옵션만으로 GC 로그: JVM `-Xlog:gc*`, Go `GODEBUG=gctrace=1`, .NET `dotnet-counters`
  - 기존 서버 로그(틱 초과 경고, 예외)를 Loki·ELK로 수집
- **경로 측정**: 대상 국가·통신사에서 합성 측정(RIPE Atlas, 클라우드 리전 VM, 상용 도구). 게임과 같은 프로토콜·포트로 mtr, DF 핑으로 MTU, UDP 유휴 테스트로 NAT 타임아웃을 잰다.
- **변경 기록**: CI에서 Grafana 주석 API를 호출해 배포·패치·설정·네트워크 작업을 모든 그래프에 세로선으로 표시한다. “패치 이후”의 출발점이다.
- **클라 쪽 (코드 변경 없이)**: 스토어 콘솔(Android vitals ANR·크래시, App Store Connect 멈춤 비율), CS 티켓을 백서의 증상 이름으로 분류, 유저용 네트워크 진단 도구(게임 서버까지 mtr·손실·MTU를 재서 올리는 별도 실행 파일).
- **사고 대비**: 서버에 패킷 캡처 링 버퍼(`dumpcap -b`)를 상시 켠다.

## 3. 최소 코드 연동: 개발팀에 요청할 6가지

코드 없이는 안 보이는 사각지대는 클라 체감(FPS), UDP 앱 레벨 RTT, 틱 내부, 끊김 사유, 시야(AOI) 로직이다. 이것만 메운다. 하나당 며칠 작업이다.

1. **클라 요약 비콘**: 30~60초마다 또는 세션 끝에. RTT p50/p95, 지터, 손실, FPS·1% low, 프레임 스파이크 수, 틱 번호 공백, 재접속 수, 망 종류, 빌드, 서버·채널, 세션 ID. 게임 연결과 별도로 기존 텔레메트리나 HTTPS로 보낸다.
2. **서버 틱 지표 엔드포인트**(Prometheus/StatsD): 틱 시간 p50/p99, 틱 초과 수, 존별 인원, 연결별 송신 대기열, 버린 업데이트 수.
3. **끊김 사유 코드 표준화**: 하트비트 타임아웃 / RST / 서버 킥 / 프로토콜 오류 / 인증 실패 / 점검을 양쪽에 같은 코드로 남긴다.
4. **상관 ID와 시간**: 세션·캐릭터·서버 ID를 모든 로그와 비콘에, NTP 동기 UTC 시각으로. 제보 하나를 서버·네트워크 데이터에 바로 붙일 수 있다.
5. **렉 신고 버튼**: 최근 60초 링 버퍼(RTT·FPS·틱 공백)를 세션 ID와 함께 올리고 CS 티켓에 자동 첨부한다.
6. **모든 텔레메트리에 빌드 버전**.

## 4. 두 시나리오의 절차

### 패치 이후 문제

1. 배포 주석으로 시작점을 확정한다.
2. 빌드별(클라 비콘)·카나리 채널별(서버)로 나눠 비교한다.
3. “트래픽 지문”의 전후를 비교한다: 유저당 pps·바이트, 평균 패킷 크기(MTU 초과 여부), 연결 수, DB QPS·쿼리 종류, 캐시 적중률, 틱 시간.
4. 지문이 바뀌었으면 증거를 붙여 개발팀으로, 지문은 그대로인데 인프라 지표가 바뀌었으면 인프라로. 같이 나간 인프라 변경도 주석에 남긴다.

### 해외 국가 추가

- **오픈 전**: 현지 통신사별 RTT 분포·지터·손실·MTU·NAT 유휴 타임아웃·UDP 제한 여부를 잰다. 그 값을 게임 설계가 버티는 한도(판정 구간, 지연 보상 한도, 타임아웃·하트비트 간격)와 비교한다. 백서의 동기화 장이 기준표다. 개인정보 규정도 확인한다.
- **담당**: 인프라(리전·엣지 PoP, 경로·피어링, 릴레이), 개발(지연 허용 설계, 하트비트·타임아웃 값, 패킷 크기, 재접속 UX), 외부(통신사).
- **오픈 후**: 국가·ASN별 대시보드와 끊김 사유 분포를 본다.

## 5. 데이터 구조

- **호스트 모니터링(Zabbix 등)**: 호스트·네트워크·DB 상태를 보기에 알맞다. 유저·세션·ASN·빌드처럼 차원이 많은 데이터에는 맞지 않는다.
- **차원 데이터**: 클라 비콘, 접속·흐름 로그, 연결별 통계는 ClickHouse, 집계 시계열은 Prometheus/VictoriaMetrics, 로그는 Loki에 두고 Grafana에서 한 화면으로 본다.
- **렉 판정 대시보드 한 장**: 판정 순서대로 구성한다.
  - 변수: 국가·ASN·서버·채널·빌드·플랫폼
  - 행: 범위 → 네트워크 → 호스트 → 앱(틱·Recv-Q) → DB → 클라
  - 배포 주석을 모든 행에 겹쳐 표시

## 6. 백서에 추가할 것

| 번호 | 내용 | 상태 |
|---|---|---|
| 1 | **신호 카탈로그 + 원인별 증거 필드**: 원인마다 확인할 곳, 이러면 맞음·아님, 가장 쉬운 확인 수단(인프라 도구·게임 로그·유저 쪽), 그래프 모양 | 구현: 원인의 `chk`·`sig` 필드(`docs/CHECKS_GUIDE.md`), 카드의 “그래프에서는”·“확인할 곳” |
| 2 | **새 장 “관측으로 판정하기”**: 판정 순서, 판정 신호표, 코드 없이 할 것 / 최소 코드, 그리고 **관측 커버리지 계산기**(가진 확인 수단을 고르면 확인할 수 있는 원인 수와 아직 안 보이는 원인 목록) | 구현: 판정 흐름 그림, 신호표, 그래프 모양 13가지, 확인 수단 계산기, 숫자 읽는 법(평균·백분위 실험) |
| 3 | **진단 도우미 확장**: 후보마다 “먼저 볼 것” | 구현: 상위 후보에 확인할 곳과 그래프 모양 표시. 답할수록 좁혀지는 판정 질문은 다음 단계 |
| 4 | **플레이북 두 개**: 패치 후 회귀, 해외 국가 추가 | 구현: “사례와 절차” 장 |
| 5 | **개발팀 계측 요청 명세서**(1~2쪽): 필드·주기·전송 방식·비용·개인정보 | 조직별 작성. 백서의 “게임 코드에 더할 것”과 계산기의 “다른 수단이 필요한 원인” 목록이 바탕 |
| 6 | **Grafana 대시보드 설계서**: 패널 목록, 항목 키·PromQL 예시 | 조직별 작성 |
| 7 | **(선택) 운영 대시보드 연결**: 백서의 신호에서 각자 운영하는 대시보드로 여는 링크. 운영 환경 주소는 저장소에 넣지 않는다 | 조직별 작성 |
| 8 | **사례집**: 장애 회고를 원인 카드에 연결 | 구현: 공개된 사후 분석 12건(`src/js/cases.js`), 원인 카드의 “실제 사례” |

## 7. 단계

| 단계 | 기간 | 내용 |
|---|---|---|
| 1 | 1~2주, 코드 없음 | 배포 주석, GeoIP·ASN 차원, eBPF·ss 연결 품질, 소켓 대기열·스레드 CPU·GC 로그, CS 증상 분류. 백서에 판정 장·신호표 |
| 2 | 2~6주, 최소 코드 | 명세서로 6가지 요청, 판정 대시보드 완성, 진단 도우미에 판정 질문 |
| 3 | 이후 | 차원별 이상 탐지로 담당 자동 제안(어느 차원에 몰렸나 → 팀), 사례집, 국가 오픈 체크리스트 정례화 |

6-1·6-2는 백서에 들어갔으니, 조직에서는 6-5(개발팀 계측 명세서)부터 만드는 것을 추천한다. 계산기에서 “게임 로그·지표”를 끈 채 나오는 원인 목록이 요청할 항목의 근거가 된다.
